# ERRATA 146 — 사슬 용량표의 가지치기 상한이 무효였다

> **철회 (RETRACTION).**  라운드 145 문서
> `research/RR_L6_PROOF_145_CLAUDE.md` 의 결론 **`L6 >= 872`** 와 **`L6 = 872`**
> 를 철회한다.  그 증명 사슬의 §8 (길이 870·871 좌표행 소거) 은 사슬(chain)
> 용량표를 **상한** 으로 사용하는데, 그 표의 값들이 참값보다 **작다**.  상한이
> 너무 작으면 닫히지 않아야 할 행이 닫힌다.  따라서 `L6 >= 871` 과
> `L6 >= 872` 는 현재 **성립이 확인되지 않은 상태** 이다.
>
> 이 문서는 원문을 지우지 않는다.  라운드 145 문서는 그대로 두고 그 머리에
> 교정 상자를 붙였다.  아래가 결함의 정확한 위치, 재현 방법, 영향 범위,
> 그리고 살아남는 결론이다.

발견: 라운드 146 (적대적 검증), 2026-09-12/13.
발견자: 이 프로젝트의 자체 감사 (외부 반례 제보 아님).

---

## 1. 결함의 정확한 위치

`src/l6_chain_capacity_144.c` 의 가지치기는 남은 예산의 **합** 으로 표를
조회한다 (라인 214–216):

```c
int left = (AMAX - au) + (BMAX - bu) + (EMAX - eu);
int reach = ports + ubound(tok, DMAX - deficit + 4 + 5 * tok, left, HMAX - hu) - 1;
```

따라서 `UB[tok][d][S][h]` 는 **세 예산의 합이 `S` 이하인 모든 분할** 을 덮는
상한이어야 한다.  즉 분할 `(x, y, z)`, `x+y+z <= S` 에 대한 **최댓값** 이어야
한다.

그런데 `src/l6_chain_rows_144.py` 의 `write_ub()` 는 캐시된 **셀마다** 한 줄,
즉 **분할마다** 한 줄을 같은 키 `S = a + bb + e` 아래로 내보냈다:

```python
lines.append(f"{b} {d} {a + bb + e} 0 {v}")        # 사슬 캐시
lines.append(f"{b} {d} {a + bb + e} {h} {v}")      # 무거운 관절 캐시
```

그리고 `src/l6_chain_capacity_144.c` 의 로더는 같은 키의 여러 줄 중
**최솟값** 을 취한다 (라인 278–280) — "여러 개의 독립 상한 중 가장 좋은 것을
쓴다" 는 자연스러운 해석이지만, 각 줄이 그 키에 대해 유효한 상한일 때만
옳다:

```c
while (fscanf(f, "%d %d %d %d %d", &bb, &dd, &aa, &hh, &vv) == 5)
    if (... && vv < UB[bb][dd][aa][hh]) UB[bb][dd][aa][hh] = vv;
```

`a`, `bb`, `e` 를 재배분할 수 없는 상태에서 잰 용량은 합만 같은 다른 분할의
용량을 덮지 못한다.  그래서 **최솟값 집계는 무효** 다.  이어지는 단조화 루프
(라인 284–289) 는 `d`, `a`, `h` 방향으로 값을 **올리기만** 하므로 같은 키의
최솟값 문제를 고치지 못한다.

캐시된 값으로 확인한 붕괴 규모: 키 425 개 중 **163 개** 에서 분할별 값이
다르다.  예를 들어 `b=0, d=0, S=10` 아래에는 20 부터 50 까지가 모여 있고,
로더는 **20** 을 골라 쓴다.

## 2. 재현

```
# 참값 (표 없이; 해석적 prune reach2 만 사용 — 그 자체로 건전)
./outputs/l6chain_144.exe 0 0 0 0  9 0 0 - 0   ->  cc = 50   (nodes    89,378)
./outputs/l6chain_144.exe 0 0 0 0 10 0 0 - 0   ->  cc = 55   (nodes   171,568)
# 무효 표를 쓴 값 = 라운드 144 가 기록한 값
./outputs/l6chain_144.exe 0 0 0 0  9 0 0 outputs/rr_l6_chain_ub_144.txt 0  ->  cc = 45
./outputs/l6chain_144.exe 0 0 0 0 10 0 0 outputs/rr_l6_chain_ub_144.txt 0  ->  cc = 40
```

두 실행 모두 `capped = false` 다.  `b = 0, d <= 1` 인 377 셀을 표 없이 전부
다시 계산한 결과 **87 셀** 이 기록값보다 크다 (즉 기록값이 참값보다 작다).
가장 큰 차이: `0|1|1|0|13` 기록 50 → 참값 69.

이 결함의 가장 노골적인 흔적은 `bound_below` 로만 기록된 6 개 셀이다.  이들은
`nodes = 1` 로 기록되어 있다 — 무효 표가 **루트에서 바로** 가지를 쳐서, 단
한 노드만 보고 `CC <= 123` 을 주장한 것이다 (예: `2|6|3|0|0`, `2|8|1|0|0`).

또한 이 결함은 표 자체의 **단조성 위반** 으로 이미 표면에 드러나 있었다:
예산을 늘렸는데 용량이 줄어드는 셀이 28 쌍 있다
(`outputs/rr_l6_table_integrity_146.json`, 검사 3).  예산은 "이하" 의미이므로
용량은 예산에 대해 단조 비감소여야 한다.  라운드 146 의 표 무결성 감사기가
이 28 건을 보고했고, 그 원인을 추적한 결과가 이 문서다.

## 3. 영향 범위 — 어떤 단계가 무너지는가

`src/l6_rows_final_144.py` 는 세 모형 (piece / split-chain / merged-chain) 의
상한 중 **최소** 를 취해 행을 닫는다.  조각(piece) 모형만으로도 닫히는 행은
이 결함과 무관하다.  각 좌표행에 대해 "조각 모형 단독으로 닫히는가" 를 다시
계산했다 (`outputs/rr_l6_chain_dependency_146.json`):

| 길이 | 좌표행 | 사슬 상한이 **필요한** 행 | 상태 |
|---|---:|---:|---|
| `L = 869` (`t = 2`) | 85 | **0** | 영향 없음 |
| `L = 870` (`t = 3`) | 353 | **61** | 확인 불가 |
| `L = 871` (`t = 4`) | 1156 | **552** | 확인 불가 |

조각 모형의 표는 이 결함과 무관하다: `src/l6_build_captable_144.py`
의 `write_ub()` 는 마스크 `00` 셀만 내보내고 (가장 느슨한 마스크이므로 같은
`(b,d)` 의 모든 마스크에 대해 유효한 상한), 키에 예산 차원이 없고, 55 개 키
전부에 **충돌하는 중복 줄이 없다**.

## 4. 지금 남는 결론

* **살아남음**: `L6 >= 870`.  `t = 2` 의 85 개 좌표행 전부가 조각 모형 단독으로
  닫힌다.  (이 결론은 §2 고정 대표원, §3–§7 MASTER 항등식, 조각 모형에만
  의존한다.  그 부분들은 라운드 145·146 에서 따로 감사되었고 이 결함과 무관하다.)
* **살아남음**: `L6 <= 872` — 길이 872 증인 (`data/verified_872_witness.txt`,
  그리고 외부 아카이브의 44,121 개 길이-872 덮개 전부가 프레임워크를 통과).
* **따라서 현재 확정 구간은 `L6 ∈ {870, 871, 872}`.**
* **철회**: `L6 >= 871`, `L6 >= 872`, `L6 = 872`.

라운드 144 의 "869 닫힘" 은 살아남고, "870 닫힘" 과 "871 을 두 등호행으로
축소" 는 살아남지 못한다.  §9 의 순수 순환 공존 논거 자체는 독립적으로
재검증되었다 (`src/l6_cover_bfs_146.py`: 세 증인 모두 `c` 개 궤도로 `F` 를 덮을
수 없고, 실제 최소 궤도 수는 8 로 여유 2·2·1) — 그러나 §9 는 §8 이 남긴 두
행만을 다루므로, §8 이 복구되지 않으면 §9 만으로는 아무것도 닫지 못한다.

## 5. 복구 작업

1. `write_ub()` 를 키별 **최댓값** 집계로 수정했다 (건전한 방향).  이것만으로는
   부족하다: 집계되는 값 자체가 무효 표를 쓰지 않은 실행에서 나와야 한다.
2. `src/l6_chain_recheck_146.py` 가 닫힘에 실제로 쓰이는 **825 개 셀** 을
   가지치기 표 없이 다시 계산한다.  표 없는 실행도 해석적 prune
   `reach2 = ports + (미사용 육각형) + (남은 예산 합)` 은 유지하므로 (포트를 하나
   더 얻으려면 새 육각형 또는 재사용 예산 한 단위가 반드시 필요) 반환값은 그
   셀의 **정확한** 용량이다.  결과는
   `outputs/rr_l6_chain_recheck_146.json` 에 기록하며, 감사 대상 라운드 144
   원장은 건드리지 않는다.
3. 그 값으로 613 개 행의 상한을 다시 계산해, 어느 행이 여전히 닫히고 어느 행이
   살아남는지 확정한다.

## 6. 부수적으로 고친 것

* `l6_chain_rows_144.compute()` 는 탐색기에 `HMAX` 인자가 추가된 뒤 갱신되지
  않아 argv 가 한 칸씩 밀려 있었다 (`node_cap` → `HMAX`, UB 경로 → `NODECAP`,
  `target` → UB **파일 이름**).  모든 호출이 `"ubfile"` 오류로 죽었다.  즉
  1,501 셀 표는 **자기 구동기로 재생성할 수 없는 상태** 였다.  인자 목록을
  `l6_871_analysis_144.heavy_cell` 이 이미 올바르게 쓰던 형태로 맞췄다.
* `compute()` 는 `_C` 를 그대로 원장에 썼다.  `_C` 는 빈 dict 로 시작하고
  `load_cache()` 만이 채우므로, `load_cache()` 없이 `compute()` 를 한 번
  호출하면 1,501 셀 원장이 **한 셀로 덮어써진다**.  이 감사 중 실제로 일어났고
  git 에서 복원했다.  이제 `_save_cache()` 가 원장을 줄이는 쓰기를 거부하고
  원자적으로 쓴다.
* `src/l6_table_integrity_146.py` 의 재실행 검사는 5 열 사슬 UB 파일을 3 열
  조각 탐색기에 넘겨 `a` 열을 용량으로 읽었다.  올바른 파일로 고쳤다.  탐색기가
  잘못된 열 수의 UB 파일을 조용히 받아들이는 것은 별도의 약점으로 남긴다.
